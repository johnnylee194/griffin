# 运势功能 Feature Spec

> 状态：v0.2
> 更新日期：2026-05-04

---

## 1. 方向与目标

### 核心定位
以**八字黄历**为中心，提供麻将相关的个性化运势解读。不追求科学性，追求「看起来专业、读起来有意思、用起来有参考价值」。

### 设计原则
- **专业感**：八字、神煞、宜忌等传统元素
- **个性化**：基于用户八字，不是通用模板
- **麻将相关**：所有内容围绕打牌场景，不谈婚丧嫁娶
- **秒出骨架 + AI 补 narrative**：结构化数据秒出，AI 解读在后台生成

## 2. 数据需求

### 用户字段扩展

| 字段 | 类型 | 说明 | 必填 |
|------|------|------|------|
| `birth_date` | TEXT | 出生日期（YYYY-MM-DD） | 已存在 |
| `birth_time` | TEXT | 出生时辰（如 "14:30"） | **新增，强制** |
| `birth_location` | TEXT | 出生地点（城市名，如"成都"） | **新增，强制** |
| `birth_latitude` | REAL | 出生地纬度（由城市名 geocoding 得到，缓存） | **新增，缓存** |
| `birth_longitude` | REAL | 出生地经度（由城市名 geocoding 得到，缓存） | **新增，缓存** |
| `gender` | INTEGER | 性别（0: 女 / 1: 男，用于乾造/坤造） | **新增，强制** |

> `birth_latitude` 和 `birth_longitude` 在用户保存出生地时通过 geocoding 服务获取，存储用于真太阳时计算，避免每次实时查询。

### 真太阳时计算
- 使用 `birth_location` 的经纬度
- 计算公式：当地平太阳时 = 北京时间 ± (当地经度 - 120°E) × 4分钟
- 不做夏令时校正（用户通常不知道自己出生时是否夏令时）

## 3. 技术方案

### 依赖库

```
lunisolar                        # 核心库，八字计算
@lunisolar/plugin-char8ex         # 八字十神、神煞
@lunisolar/plugin-takesound      # 五行纳音
@lunisolar/plugin-thegods        # 神煞宜忌（基于《协纪辨方书》）
geocoding                        # 城市名 → 经纬度（用于真太阳时计算）
```

> 注：使用 **高德地图 API**（AMap）进行城市名 → 经纬度转换。需要 `AMAP_API_KEY` 环境变量。QPS 限制视套餐而定，已缓存结果到用户表。

### 黄历数据（lunisolar 库自带）

| 数据 | 说明 | 获取速度 |
|------|------|----------|
| 八字四柱 | 年柱、月柱、日柱、时柱 | < 1ms |
| 纳音五行 | 如「剑锋金」「山头火」 | < 1ms |
| 十神 | 比肩、劫财、正官… | < 1ms |
| 神煞 | 文昌贵人、驿马星… | < 1ms |
| 每日宜忌 | 宜打牌、忌大规模投资… | < 1ms |
| 吉神方位 | 财神、喜神、福神方向 | < 1ms |
| 凶煞方位 | 煞神方向 | < 1ms |
| 黄道黑道 | 黄道日/黑道日 | < 1ms |

### AI 用途
仅用于**生成 narrative 解读**，结构化为：
- 今日整体运势描述（3-5 句话）
- 针对麻将的具体建议
- 吉祥方位和时间段的解读
- 需要注意的警示（如有）

### 性能目标
| 阶段 | 目标 |
|------|------|
| 结构化黄历数据（lunisolar） | < 100ms |
| AI narrative 生成 | 10-30s（不可控） |
| 页面可交互时间 | < 500ms（骨架先出） |

#### Phase 3 目标：7+1 维度两屏结构

**第一屏（快速决策）**
- 今日运势总判断（旺/平/弱 + 一句话）
- 投注策略（大注/小注/观望）
- 今天最适合做什么（麻将专项）
- 黄金时段（12时辰，当前时辰高亮）
- 最佳方位

**第二屏（深度阅读）**
- 冲煞空亡警示
- 宜忌清单
- 面相观察点
- 颜色/数字

详见 `docs/CR-DESIGN-LOOKUP-AND-FACE.md` Section 三。

### 预设问题清单

**静态问题（所有人都一样）：**
1. 「今天打牌有没有什么禁忌？」
2. 「今天适合打大牌还是小注？」
3. 「今天财神在哪个方向？」
4. 「有没有什么吉祥数字或颜色？」

**动态问题（需要用户战绩数据）：**
1. 「基于我最近的运气，今天适合翻本还是见好就收？」
2. 「我这周手风如何？有什么建议？」
3. 「我上次在[最近去过的地方]输了，今天还适合去吗？」

### 交互流程

1. 用户进入黄历 Tab
2. **立即**：展示八字日期 + 结构化黄历数据（宜忌、财神方位等）
3. **立即**：展示 AI narrative 的骨架（loading 状态）
4. **后台**：调用 AI 生成 narrative，完成后替换骨架
5. 展示预设问题列表（静态全显示，动态需要战绩数据才显示）
6. 用户点击问题 → 触发 AI 生成答案 → 展示

### 错误处理

| 场景 | 处理 |
|------|------|
| 缺少 `birth_time` | 引导用户去设置，不展示黄历 Tab |
| 缺少 `birth_location` | 引导用户去设置，不展示黄历 Tab |
| 缺少 `gender` | 引导用户去设置，不展示黄历 Tab |
| AI 生成失败 | 展示结构化数据 + 「AI 解读生成失败，请稍后重试」 |
| 网络离线 | 展示最后缓存的结构化数据 + 提示「离线，无法生成新解读」 |

## 5. 数据流

```
用户进入
    ↓
检查用户字段（birth_date + birth_time + birth_location + gender）
    ↓ 缺失 → 引导补充
    ↓ 完整
构建 lunisolar 实例（日期 = 今日，出生信息 = 用户信息）
    ↓
计算真太阳时校正
    ↓
调用 lunisolar.char8ex() 获取八字
    ↓
查询今日黄历数据（神煞、宜忌、吉神方位）
    ↓
[并行]
  ├→ 立即渲染：八字日期 + 结构化黄历（< 100ms）
  └→ AI 解读请求（prompt 含八字 + 黄历 + 用户战绩）
          ↓
      AI 返回 narrative
          ↓
      渲染 AI 解读（替换 loading 状态）
```

## 6. Prompt 设计

### Phase 2 Prompt（当前实现）

单段落 narrative prompt，详见 `backend/src/utils/horoscope.ts` 的 `buildHoroscopePrompt`。

```
你是一位中国传统黄历解读师，专门为麻将玩家提供运势指导。

用户信息：
- 八字：[八字]
- 今日黄历：宜[xxx] 忌[xxx] 财神[方向] 喜神[方向]
- [可选]近期战绩：[战绩摘要]

请用大白话解读，不需要出现「驿马星」「财库」「命宫」等术语。

输出格式：
- 一段话描述今日整体运势（3-5句）
- 针对麻将的具体建议（2-3句）
- 如果有警示，加上提醒（1-2句）

语气：轻松但有参考价值，不要过度乐观或悲观。
```

### Phase 3 Prompt（7+1 维度，详见 CR-DESIGN-LOOKUP-AND-FACE.md Section 五）

每个维度单独生成 prompt，包含：
1. 原始数据：该维度的八字原始值
2. 术语解释：词义 + 五行含义
3. 能量解读：旺/弱代表什么
4. 麻将连接：对打牌意味着什么
5. 行动建议：今天应该怎么做

详见 `docs/CR-DESIGN-LOOKUP-AND-FACE.md` Section 五。

## 7. Loading 设计

详见 `docs/CR-DESIGN-LOOKUP-AND-FACE.md` Section 七。

设计要点：
- 纯表演性，缓解用户焦虑，非真实进度
- 总时长约 10 秒，分 6 步，每步约 1.5 秒
- 文案库随机/轮流，避免重复
- 最后一步完成后淡出，展示真实内容

## 9. Open Questions → 已确认

~~1. **出生地点存储格式**：存城市名还是经纬度？城市名需要额外 geocoding 库转换。~~
→ 存**城市名**，经纬度在计算时通过 geocoding 库实时转换（或缓存一份在用户表）

~~2. **历史记录保留**：是否保留每日黄历快照？保留多久？~~
→ **不做历史存储**。每天的运势是当时快照，过了就过了。用户想回顾可以截图。

~~3. **AI 生成并发控制**：同一用户同时点多个问题，是否排队还是并行？~~
→ **不允许并发**。点了一个问题，其他问题隐藏 → 显示进度 → AI 返回 → 展示结果 → 问题恢复

~~4. **用户修改出生信息后**：历史黄历是否需要重新生成？~~
→ **自动重新生成**。用户修改 birth_date / birth_time / birth_location / gender 后，触发全量重新生成
